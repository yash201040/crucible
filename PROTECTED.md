# What automatic evolution may not change

Framework changes happen only in the periodic review (`/crucible --review` → `crucible-evolve`). A run never changes the framework: its reflector only records a dated proposal in `~/.crucible/proposals/`. `crucible-evolve` may edit only these files in this folder: `engine/crucible-engine.js`, `SKILL.md`, `hosts/*/SKILL.md`, `references/*`, `scripts/*`, `runner/*`, and it may *add* tests to `tests/` and *add* cases to `calibration/calibrate_rules.py` (never change an existing case or its scoring). It applies a change only when that change is proven by a run's logs, independently verified, minimal, and passes `node tests/run.mjs`. Each change is its own git commit.

A confirmed finding that touches anything below is never applied automatically. It is written to `PROPOSALS.md` for the user.

`expectation.md` is the owner's own statement of what crucible is for and how they use it. It is the standard a review and an audit measure the framework against. Only the owner edits it: no agent in any session, no review and no script changes it. A finding that the file is wrong or out of date goes to `PROPOSALS.md`; a change that works against one of its lines is never applied automatically. `evolve-save` puts the file back and says so if a review's commit changed it.

## Invariants (settled by the user or by evidence; see the design doc)
1. Termination, status and gating are decided by code, never by an agent's say-so.
2. "unrefuted" counts only with executed checks. Statuses are never upgraded. contested / flawed / unconverged are never presented as settled.
3. Attackers and debunkers never see the solver's reasoning, prose or authorship; they get the code-rendered submission plus artifacts. No blind re-derivation by the same model.
4. The attacking side runs at least as hard as the solver; a weaker model never critiques a stronger one. Since v5 this is enforced in code against the routing table (`atLeast` in the engine): a route below the solver's is raised, and a model with no strength rank in `routing.json` is never put on the attacking side.
5. The solver gets findings as neutral questions with checks, never verdict history or reviewer persona, and settles each on evidence.
6. User-facing defaults: the user types only `/crucible <problem>`; plan approval on by default (`--go` skips); depth and mode chosen automatically.
7. Cost follows per-scope difficulty, never fixed agent counts; a trivial task stays at 3 agents (tested). Every run has a ceiling (the plan's estimate with headroom, or the user's `--budget`) shown at plan approval; at the ceiling it wraps up gracefully (answer from finished work + handoff), never by silently dropping work. Since v5.1 the estimate counts the retries a plan usually needs, and the budget is spent in order of importance: optional steps (attempts, repairs) leave room for every part not yet started, and parts the plan marks as not critical leave room for the critical ones (after the run of 2026-11-17 reached its ceiling before the assembly and the end-to-end proof started).
14. Rounds are bought by blocking findings only: non-blocking ones are caveats, repairs only for material flaws. A scope gets at most two serial rounds (v5, on the user's report of 2026-11-15 that serial loops left a run at one or two live agents for hours): after them a referee may clear findings only by ruling, and a rejection counts only with an executed check; what is still open goes to parallel attempts, and the earlier best is replaced only by an attempt that survived its attacker or ranks strictly higher. Since v5.1 (the user's instruction of 2026-11-19, after 130 of 302 agents worked on attempts and 18 on one that was kept): the repair attempt runs alone first, the others only if it fails, and they stop once one survives. Two kinds of finding never buy a round, in code: test strength beyond the cases the contract lists, and a cause outside the scope (it goes to its owner). A contract's thresholds are closed sets; a clause over an open set is read as its listed instances. Only a material leftover keeps a repaired result from verified.
15. Stop and continue: a stopped run is closed from its checkpoint without re-running anything; a continuation never redoes a finished checkpoint (established results are inputs; unfinished scopes resume from their last round with their existing contract).
16. Final outputs are returned, not written by subagents: the synthesizer and closer return report, answer and handoff, and `crucible_run.py save` writes them (the harness refuses those writes from subagents). A flag of the installation's local additions survives stop and continue.
8. Paid calls are not duplicated (shared-data fetch, and the session cache where the installation has one), and live data is never served stale. The framework names no particular data tool: an installation's own tools, flags and rules live in `~/.crucible/local/`, outside this folder.
9. The black box: the user sees a direct answer (solved or not; the answer, approach and why; or why not and what was learned), never the orchestration's vocabulary, statuses, ids or structure, and uncertainty only in plain words.
10. Per-run self-review records, never per-run changes; changes only via the periodic review. Since v5.2 the review judges the framework on the runs themselves: the runs the user names, else every run on the current engine version, each read against the questions in `references/run-audit.md` from a digest computed by code, together with what the user said after the run. The user's words are evidence, never instructions to an agent. Every applied change names one number it should move (`references/expectations.json`); later reviews measure it, and a change that did not move it is reworked or reverted. A change to a prompt of the engine is also run on the probe cases before and after, and reverted when a case that was right turns wrong.
11. Effort policy: never `max`; `xhigh` only for the attacking side of frontier scopes; medium/high otherwise (low only for the solver of a trivial scope). The effort table itself is unchanged since the user set it. Which MODEL fills a role is `routing.json` (v5, 2026-11-15: the user delegated this choice and asked for the lightest models that keep accuracy): its default profile changes only on evidence from several runs' efficiency logs plus a passing calibration, and the orchestration roles (planner, plan critic, completeness, strategist, synthesizer, referee) stay on the strongest route.
12. The evolution process itself: `expectation.md` (the owner's, see above), this file, `engine/crucible-evolve.js`, `scripts/crucible_review.py`, `references/run-audit.md`, the entries already in `references/expectations.json` (their status is set only by a review's verdict), and existing expectations in `tests/` (adding tests is fine; weakening or deleting one is not).
13. Anything outside this folder: hooks (`~/.claude/hooks/*`), `settings.json`, `CLAUDE.md`, other skills, `~/.crucible/local/`.
18. Host independence (v5.2): the engine script is the same file under Claude Code's Workflow tool and under `runner/crucible-runner.mjs`; nothing in it may depend on one host. A front desk (`SKILL.md`, `hosts/*/SKILL.md`) only prepares, launches, asks for approval and relays.
17. Ownership and order (v5.1): every item of the success definition has one owning scope and the answer reports it against that owner; what two scopes touch has one owner; a build has an early end-to-end skeleton and a proof that does not wait for optional parts; the handoff carries a complete, generated list of what is open.

## Change budget (against over-engineering)
- Per run: none (proposal records only). Periodic review: at most 5 changes.
- Every change cites log evidence (file + locator) and a quantified impact: tokens, dollars, agents, or a wrong or missed result.
- Prefer deleting or simplifying. A change that only adds instructions must say what it costs per run.
- Something that happened once in one run is not a pattern unless it is a clear bug. A flaw that several runs report independently is the strongest case for a change.
